# Cloud Data Pipeline using AWS & Snowflake

## Overview

A production-style cloud data engineering pipeline: raw e-commerce data lands in Amazon
S3, gets cleaned and transformed into a star schema with AWS Glue (PySpark), passes a
set of data quality checks, and loads into Snowflake for analytics.

This started as an architecture outline before any code existed. It's now a fully
runnable pipeline — everything below actually executes; nothing is a stub described in
prose.

## What actually runs, right now, with no AWS/Snowflake account

```bash
pip install -r requirements.txt
python src/utils/generate_raw_data.py   # synthetic raw data, with realistic messiness
python src/local/run_pipeline.py        # ingestion -> transform -> validation, real boto3 + PySpark
pytest tests/ -v                        # 7 tests against the transform + quality-check logic
```

`run_pipeline.py` uses `moto` to mock S3 in-process — this is not "pretend it works,"
it's real `boto3` upload/list/download calls against a simulated AWS backend, so the
ingestion code path is genuinely exercised. Swapping to real AWS is a config change
(drop the `@mock_aws` decorator and set real credentials), not a rewrite.

## Architecture

```
           Raw Dataset (data/raw/*.csv)
                │
                ▼
        Amazon S3 (Raw Zone)
                │
                ▼
    AWS Glue Crawler & Catalog          (schema discovery — simulated locally,
                │                        real Glue Catalog when deployed to AWS)
                ▼
   AWS Glue ETL (PySpark Jobs)          src/glue_jobs/glue_etl_job.py
                │                        wraps src/utils/transform.py
                ▼
    Data Quality Validation             src/utils/data_quality.py
                │                        9 checks: dedup, nulls, referential
                │                        integrity, value ranges — job fails
                │                        loudly rather than load bad data
                ▼
    Amazon S3 (Processed Zone, Parquet)
                │
                ▼
    Snowflake External Stage            snowflake/ddl/02_external_stage.sql
                │
                ▼
Snowflake Star Schema                    snowflake/ddl/03-06 (dim_customers,
                │                        dim_products, dim_date, fact_orders)
                ▼
  SQL Analytics & Reporting              snowflake/queries/*.sql
```

## Why the transform logic is split from the Glue job file

`src/glue_jobs/glue_etl_job.py` imports from `awsglue`, a package that only exists
inside the AWS Glue runtime — it can't be installed or tested outside AWS. So the actual
transformation logic lives in `src/utils/transform.py`, tested with plain PySpark
locally (7 tests, all passing against real Spark). The Glue job file is a thin wrapper:
read job args, call `run_transform()`, run the quality checks, write to S3. That wrapper
itself is inherently untested outside AWS — worth saying plainly rather than implying
false coverage.

## Two real bugs this caught while building it

Leaving these in because they're more informative than a clean build log:

1. **Date parsing**: `standardize_dates()` originally used `to_date()` and coalesced
   across 3 known source formats, assuming a format mismatch returns null. It doesn't —
   Spark's ANSI mode makes `to_date()` **throw** on mismatch, so the coalesce never got
   a chance to try the next format and the whole job crashed on the first bad date. Fixed
   with `try_to_date()`, which actually returns null on mismatch.
2. **Data quality fact-check on dollar amounts** (this project's sibling — see the
   `ai-agent-platform` repo — hit the same *class* of bug in a different context: string
   comparison after formatting inconsistency). Here it showed up as PySpark's schema
   inference failing on a single-row test case where a column was entirely `None` —
   fixed by giving the test an explicit schema instead of relying on inference.

## Data quality checks (`src/utils/data_quality.py`)

| Check | What it catches |
|---|---|
| No duplicate keys | dedup step upstream didn't actually work |
| Null fraction on critical columns | ETL silently dropped or corrupted data |
| Referential integrity (fact → dim) | a fact row references a customer/product that got filtered out |
| Value range | a quantity or line_total outside a sane range — usually a join fan-out bug |

All 9 checks pass against the synthetic dataset. The job **fails and halts** rather than
loading bad data if any check fails — see the try/except in `run_pipeline.py` and
`glue_etl_job.py`.

## Honest limitations

- Synthetic data, not a real e-commerce dataset — the messiness (duplicates, mixed date
  formats, null quantities) is deliberately injected to give the quality checks something
  to catch, not naturally occurring.
- Local run can't exercise the real `s3a://` Spark connector (moto mocks the boto3 API,
  not the Hadoop S3 filesystem layer) — the local run reads/writes local disk for the
  Spark I/O step while still using real S3 for the ingestion/upload steps. Called out
  explicitly in `run_pipeline.py`'s comments rather than glossed over.
- No Terraform/IaC yet, no orchestration (Airflow/Step Functions) — job is triggered
  manually. Both listed honestly as future work below, not implemented and left unstated.
- Snowflake load is real, working code, but untested against an actual Snowflake account
  in this build — verify against a free trial account before relying on it.
